# MUSTER v1 Specification

**Goal:** Pin every open item from docs/architecture.md so a later implementation plan
can build v1 with zero design judgment: task file schema, bin/ script contracts,
RUNNER.md location (section 6), task templates, dispatch UX wording.

**Inputs:** docs/problem.md, docs/architecture.md, docs/decisions.md (D1-D26). All settled.
This spec adds detail; it does not reopen decisions. Where a mechanic was undecided at
the D-level, the choice is made here and marked `[spec decision]` with a one-line why.

**PoC constraint (D16):** Claude Code desktop only. Fable 5 orchestrates and reviews
(tier strong). Sonnet 5 executes (tier any). Codex support is specified where it is
free (harness field, pinning checks) but wrappers stay dormant.

---

## 1. Data plane layout

Installed by `muster:init` in the target repo:

```
tasks/
  backlog/          dependency-blocked tasks
  inbox/            ready to claim
  doing/            claimed, in progress (max 1 occupant, D18)
  done/             completed + sidecars
  failed/           terminal failures + sidecars
  archive/          archive/<plan-id>/ per closed plan
  staging/          reviewer-authored fix tasks awaiting validation by bin/done
  bin/              claim / verify / done / promote / lint / status (.ps1 + .sh each)
  RUNNER.md         executor contract (section 6)
  plan-<id>.md      plan snapshot, one per sharded plan (D23)
```

Every folder ships with a `.gitkeep`. `staging/` is new relative to architecture.md
`[spec decision]`: the reviewer needs a place to author a fix task that is not yet
validated; writing directly to inbox/ would make an invalid task claimable.
staging/ is transient - it holds at most one file, only during a `bin/done fail`
run; `bin/claim` refuses while it is non-empty (stale orphan, human clears).

`muster:close` moves the plan snapshot `plan-<id>.md` into `archive/<plan-id>/`
together with the plan's cards.

## 2. Task file schema

### 2.1 Filename and id

```
<plan-id>-<seq>-<slug>.md            impl / review / integration
<plan-id>-<seq>-fix<g>-<slug>.md     fix tasks (g = 1 or 2)
```

- `plan-id`: kebab-case, `[a-z0-9-]+`, matches the `tasks/plan-<plan-id>.md` snapshot.
- `seq`: two digits, `01`-`98` assigned by shard in DAG order. `99` is reserved for the
  terminal integration task (D24). A plan needing more than 98 tasks must be split.
- `slug`: kebab-case short name.
- Fix tasks reuse the seq of the impl task they fix, plus `fix<generation>`.
  The reviewer stages a fix WITHOUT the generation digit
  (`<plan-id>-<seq>-fix-<slug>.md`); `bin/done fail` computes the generation
  and stamps it into the filename, `id`, `generation` field, and title line
  when it accepts the fix (mechanics belong to scripts, D17).
- Task id = filename minus `.md`. Frontmatter `id` must equal it exactly.
- Shard refuses any filename that already exists anywhere under tasks/ (D23).

### 2.2 Frontmatter fields

Strict YAML subset (section 2.5). Full field table:

| Field | Type | Required on | Written by | Meaning |
|---|---|---|---|---|
| `id` | string | all | shard (fix: reviewer) | Equals filename stem. |
| `plan` | string | all | shard | Plan id. Groups tasks (D13). |
| `type` | enum | all | shard | `impl` / `review` / `fix` / `integration`. |
| `tier` | enum | all | shard | `any` / `strong` (D25). PoC: any = Sonnet 5, strong = Fable 5. |
| `harness` | enum | optional | shard | `claude` / `codex`. Absent = either. Required when verify needs network (D16). |
| `depends_on` | list of ids | all (may be `[]`) | shard; `bin/done fail` appends fix id to the review task | Promotion gate (D7). |
| `reviews` | id | review | shard | The impl task this review gates. |
| `fixes` | id | fix | reviewer | The impl task this fix repairs. Generation counting keys off this. |
| `generation` | int | fix | `bin/done fail` | 1 or 2. Absent in staging/; stamped on accept. A third generation is never written (D11). |
| `protected` | list of paths | impl, fix | shard (fix: reviewer) | Files verify depends on. `bin/done` refuses if diff touches them (D20). |
| `commit_paths` | list of paths | impl, fix | shard (fix: reviewer) | Exact stage list for the completion commit (D21). Review/integration: omit (their outputs are sidecars only). |
| `verify` | list of maps | all | shard (fix: reviewer) | Tier-0 block, section 2.4. |
| `claimed_at` | ISO 8601 UTC | stamped at claim | `bin/claim` | Absent until claimed. Stale threshold: 24h `[spec decision]` - one working day; shorter would flag overnight sessions. |

Notes:

- There is no `review:` flag on impl tasks. Review opt-in (D10) is expressed by the
  existence of a review task with `reviews: <impl-id>`, nothing else.
- `generation` appears only on fix tasks and only the script computes it:
  the number of existing files with `fixes: <impl-id>` anywhere under tasks/
  excluding staging/, plus one. The reviewer never counts. Generation 3 is
  never stamped: two landed fixes = cap hit (D11).

### 2.3 Body sections

Required in this order. Lint checks headings exactly.

```markdown
# <id>: <title>

## Context
Inlined excerpts only (D23). Self-contained: everything the executor must know,
pasted in, never pointed at. May quote the plan snapshot; may not tell the
executor to open it.

## Steps
Numbered. Target-state phrasing ("ensure file X contains ..."), not actions,
so recovery re-dispatch is idempotent (D12). Exact paths, exact content or
exact diffs. Zero judgment calls (D9).

## Acceptance
Human-readable bullet list of what done means. Informational - the verify
block is the authoritative check.
```

Review tasks use the same headings; their Steps are the review checklist
(section 7.2). Fix tasks inline the reviewer findings in Context.

### 2.4 Verify block format

Frontmatter, not fenced body block - scripts already parse frontmatter, one parser.

```yaml
verify:
  - cmd: "dotnet test Tests/Auth.Tests.csproj"
    expect_exit: 0
    timeout_seconds: 600
  - cmd: "node scripts/check-schema.js"
    expect_contains: "SCHEMA OK"
```

Rules:

- `cmd`: one executable plus arguments. Tokenized by the script respecting double
  quotes, invoked directly - **no shell interpretation**. No pipes, redirects, `&&`,
  `;`, backticks, or subshells. This makes ps1 and sh behavior identical.
- Expectations: `expect_exit` (int) and/or `expect_contains` (literal substring,
  case-sensitive, matched against merged stdout+stderr). At least one required.
  Both present = AND.
- `timeout_seconds`: optional, default 300. Timeout = attempt fails.
- Network-free (D16) unless the task carries `harness: claude` explicitly.

### 2.5 Strict YAML subset

Scripts hand-parse frontmatter. Only these constructs are legal:

- Flat `key: value` scalars - unquoted or double-quoted strings, ints, ISO timestamps.
- Empty list `[]` inline.
- Block lists of scalars (`- item`).
- The `verify` block list of flat maps with keys `cmd`, `expect_exit`,
  `expect_contains`, `timeout_seconds` only.
- No anchors, aliases, multiline scalars, nested maps, flow maps, or comments
  inside values.

Anything else = malformed; `bin/claim` refuses loudly (D17).

### 2.6 Shard-lint checklist (D22)

Run by `muster:shard` as its final step against every file it wrote. Any failure
rejects the shard output; nothing lands in tasks/.

1. Frontmatter parses under the strict subset; all required fields for the `type`
   present; enum values legal.
2. `id` equals filename stem; filename matches the pattern in 2.1; no filename
   collision anywhere under tasks/.
3. Every `depends_on` id exists - in this shard batch or already on disk.
4. Verify block: at least one `cmd`; every entry has an expectation; no shell
   metacharacters (`| > < && ; $( )` backtick); network denylist (`curl`, `wget`,
   `git fetch/pull/push`, `npm install`, `npm ci`, `dotnet restore`, `nuget`,
   `pip install`, `Invoke-WebRequest`, `iwr`) hits only allowed when
   `harness: claude`.
5. Impl and fix tasks only: every repo path named in a verify `cmd` appears in
   `protected` or `commit_paths`. (`commit_paths` membership covers artifacts
   the task itself creates and its verify then runs. A created artifact that is
   also a grader is dual-listed: `commit_paths` to author it, `protected` to
   freeze it for downstream consumers (5b, D30). This is not impossible to
   complete - the done protected-check is tracked-diff-only (4.3 pre-3), so a
   newly-created protected path passes at authoring time; `commit_paths`-only
   was never required. Review and
   integration tasks are exempt: their `commit_paths` is empty, so the done
   scope check already refuses any code change - protecting verify inputs is
   redundant there. Heuristic: a token containing `/` counts as a repo path
   unless it starts with `-` or is a single-letter slash switch like the `/c`
   in `cmd /c npm test` - the Windows shim front from the shard skill.)
   5b. (M2 amendment) A test-looking verify path (a `tests/` or `test/` dir
   segment, or `.test.` / `.spec.` / `_test.` / `.Tests.` naming) satisfied
   only by `commit_paths` is rejected: that file is the executor-writable
   grader - the delete-the-test pass. Test paths must be `protected` (a test the
   task authors is dual-listed - `protected` and `commit_paths` - per D30; a test
   it merely runs is `protected` alone).
   Case-insensitive on both engines. Heuristic, documented as such.
6. Size cap: task file <= 300 lines and <= 16 KB. Bigger = the task is not small
   enough; reshard.
7. Placeholder scan: `TBD`, `TODO`, `FIXME`, `<fill`, `{placeholder`, `...` as
   sole step content. Any hit = reject.
8. Un-inlined reference scan: `see docs/`, `refer to`, `as described in`,
   `per the plan` = reject (D23). Heuristic, documented as such.
9. Judgment-language scan in Steps: `if needed`, `as appropriate`,
   `appropriately`, `handle edge cases` = reject (D9). Heuristic.
10. Body headings present in order: Context, Steps, Acceptance.
11. Exactly one `type: integration` task with seq `99`, `tier: strong`, and
    `depends_on` listing every other task id in the plan (D24).
12. Every review task's `reviews` id exists in the batch; a review task's
    `depends_on` entry for its impl task matches its `reviews` field.
13. `commit_paths` non-empty on impl and fix tasks.
14. (M2 amendment) Impl and fix tasks whose verify invokes a known test runner
    (`npm|pnpm|yarn test`, `dotnet test`, `pytest`, `go test`, `cargo test`,
    `Invoke-Pester`, `ctest`, `vitest`, `jest`, `mocha`, `rspec`, `phpunit` -
    word-bounded, case-insensitive on both engines) must have non-empty
    `protected`: `protected: []` plus a runner is the delete-the-test pass
    linting clean. Denylist heuristic, documented as such.

`bin/done fail` runs checks 1-10, 13, and the M2 additions 5b/14 (lint-lite)
against reviewer-authored fix
tasks in staging/ before accepting them. In lint-lite mode: check 2's collision
scan exempts the candidate file itself (it is already on disk in staging/), and
`generation` must be ABSENT with the staged gen-less filename - the script
stamps both on accept (2.1).

## 3. Sidecar formats

Sidecars are the only executor output (D17). They live next to the task file and
move with it. Contract by folder:

- done/ holds task + `.result.md` + `.verify.log`, plus any `.gen<g>.*` history
  from earlier review cycles.
- failed/ holds task + `.verify.log` (+ `.notes.md` if written) and, for
  review-cap failures, `.result.md` with the fail verdict.
- backlog/ holds `.gen<g>.result.md` / `.gen<g>.verify.log` history next to a
  cycled review task (section 4.3 fail path); a fresh round always starts with
  no live `.verify.log`, so the attempt counter resets per round.
- doing/ holds the live `.verify.log` and `.notes.md` mid-session.

### 3.1 `<id>.result.md` - written by `bin/done`

```markdown
# Result: <id>

- status: done | failed | cycled    (cycled = review failed under cap, task re-blocked on its fix)
- verdict: pass | fail              (review / integration tasks only)
- claim_commit: <sha>
- claimed_at: <iso>
- completed_at: <iso>
- verify: <one of the four forms below>
- files_changed:
  - <path>                      (see below - worktree state at assembly)

## Surprises

<folded verbatim from <id>.notes.md; literal "none reported" if the notes file
was absent>

## Findings                     (review / integration tasks only)

<folded verbatim from the notes file - the reviewer's findings and rationale>
```

`files_changed` is `git diff --name-only <claim_commit>` PLUS
`git ls-files --others --exclude-standard`: a bare diff misses exactly the normal
impl output, a newly created file. The sidecar itself never appears in the list -
it is assembled outside the worktree and moved in, so the untracked sweep cannot
see it.

The `verify:` line has four forms; the script picks one, the model never writes it:

| Line | Condition |
| --- | --- |
| `verify: pass (attempt <n> of 3)` | `<n>` counted attempt-marker commits since the claim (D28), i.e. `bin/verify` ran at least once. |
| `verify: pass (done-check only)` | Zero counted attempts - the task went straight to `bin/done` and only the done-check ran. |
| `verify: pass (claim-probe)` | Zero counted attempts and the task was auto-filed by the claim recovery probe (4.1.9). |
| `verify: FAIL (done-check red - see verify.log)` | The done-check went red and a `fail` verdict was filed anyway (review / integration, D29, 4.3). Overrides the other three, so the sidecar never claims pass while the co-located `verify.log` shows FAIL. |

Everything above `## Surprises` is assembled from git and the verify log by the
script. The model contributes only the notes file (D17).

There is no `completion_commit` field: the sidecar is staged inside the
completion commit, so it cannot contain that commit's own sha. The completion
commit is derivable as the commit that introduced the sidecar
(`git log -n1 --format=%H -- <sidecar-path>`).

### 3.2 `<id>.verify.log` - written by `bin/verify`

Append-only. One block per attempt:

```
=== attempt 1 | 2026-08-07T09:14:02Z | task <id> | HEAD <sha>
$ dotnet test Tests/Auth.Tests.csproj
<merged stdout+stderr>
exit 0 | expect_exit 0 -> OK
=== attempt 1 result: PASS
```

- Attempt counting (D28) = `git rev-list --count <claimCommit>..HEAD --grep
  '^muster(<plan>): attempt <n> <id>$'` - marker commits, not log content. Before
  running any verify command, `bin/verify` commits the attempt header to this log
  alone with that exact message; it is the ONLY per-attempt commit and is
  exit-code-checked (a failed marker commit refuses rather than let an attempt
  run unaccounted). Truncating or deleting the log cannot lower the count - it
  lives in commit history, not file content.
- `bin/done`'s confirmation run is logged with header `=== done-check` and does
  not count toward the cap of 3.
- `bin/claim`'s pre-execution recovery probe is logged with header `=== claim-probe`
  and does not count toward the cap.

### 3.3 `<id>.notes.md` - the one file the executor writes

Free text in `tasks/doing/`. Impl/fix: one paragraph of surprises, optional.
Review/integration: verdict rationale and findings, **required** - `bin/done`
refuses `pass`/`fail` on a review task without it. Folded into result.md and
deleted by `bin/done`.

## 4. bin/ script contracts

### 4.0 Shared conventions

- Four verbs only (D17): `claim`, `verify`, `done`, `promote`. Each ships as
  `.ps1` and `.sh` with identical behavior; this spec is language-neutral.
  PoC implements ps1 first.
  `lint` (2.6) and `status` (8.3) also ship in bin/ but are not RUNNER verbs -
  humans and the orchestrator call them; executors never do.
- Scripts run from anywhere inside the repo; they locate tasks/ via
  `git rev-parse --show-toplevel`.
- Exit codes: `0` success/pass; `1` refusal (precondition failed, message says
  which); `2` verify attempt failed, retry allowed; `3` terminal (task moved to
  failed/).
- Refusal messages are single lines starting `MUSTER refuse:` so executors can
  quote them verbatim (RUNNER rule).
- Commit messages: `muster(<plan>): claim <id>` / `done <id>` / `fail <id>` /
  `reject <id> gen<g>` / `muster: promote <n>`. Scripts never use `git add -A`;
  every staged path is explicit (D21).
- All transitions are renames within tasks/ followed by a commit - never delete
  and recreate.
- Occupancy checks (doing/ occupied, sole occupant, staging/ non-empty) count
  only task `.md` files. `.gitkeep`, sidecars, and notes files never count.

### 4.1 `bin/claim -Harness <claude|codex> -Tier <any|strong>`

Identity flags are mandatory - the wrapper skill supplies them (D25).

1. Run `promote` in commit mode (self-heal, D7). Promote only renames inside
   tasks/, so a dirty tree does not block it.
2. Print the status block (section 8.3). This happens before any refusal - the
   status print is the stale/dead-block detector (D12) and must fire exactly
   when the board is unhealthy.
3. Refuse if doing/ is occupied: one executor per checkout (D18). Message names
   the occupant and its claimed_at, and points at RUNNER.md RECOVERY.
4. Refuse if staging/ is non-empty - a stale orphaned fix from a crashed
   `done fail`; the human clears it per RECOVERY.
5. Select the task: the lowest filename in inbox/ whose pinning matches - there
   is no manual selector; dependency order is the only order that matters.
   Pinning: task `tier: strong` requires `-Tier strong`; `-Tier strong`
   sessions claim **only** `tier: strong` tasks (strong quota is reserved for
   judgment, D16); task `harness` set and different from `-Harness` =
   ineligible. Nothing eligible = refuse with "nothing to claim for
   <harness>/<tier>".
6. Validate frontmatter (strict subset, required fields). Malformed = refuse
   loudly, task stays in inbox/ for the human.
7. Dirty-tree scope check: refuse if any dirty path falls outside the selected
   task's `commit_paths` union the executor-writable set under tasks/:
   `doing/*.notes.md`, `doing/*.verify.log`, `staging/*.md`. Any other dirty
   path under tasks/ - bin/ scripts, RUNNER.md, task cards, done//failed/
   history - refuses: the board is protocol surface, never the executor's to
   edit (D27). `[spec decision]` - the check is scoped
   to the selected task rather than blanket, because the D12 crash shape IS a
   dirty tree holding the recovered task's own half-done work; a blanket refusal
   would force the human to destroy exactly the work the recovery probe exists
   to detect. Dirt belonging to any other task still refuses (chimera-commit
   guard, D18).
8. Rename inbox/ -> doing/, stamp `claimed_at`, commit both changes as the claim
   commit (D21).
9. Recovery probe (D12) - runs ONLY when both hold: `type` is `impl` or `fix`,
   AND git history shows a prior claim commit for this id
   (`git log --oneline -- "tasks/doing/<id>.md"` non-empty before this claim).
   `[spec decision]` - an ungated probe would auto-file every review and
   integration task (their verify is green before the judgment work happens)
   and any impl task whose verify passes pre-work; gating on re-dispatch
   evidence preserves D12's intent without destroying tier 1.
   Probe: run the verify block once (logged as `=== claim-probe`). All green =
   a crashed predecessor already did the work: run the done-flow preconditions
   (protected + scope checks; failure = refuse for a human), assemble result.md
   (Surprises: "auto-filed at claim: verify green before execution"), move task
   + sidecars to done/, make the completion commit, run promote in no-commit
   mode folded into that commit, then **go back to step 5** to select the next
   task.
10. Print the full task body followed by: `Claimed <id>. Follow tasks/RUNNER.md.`

### 4.2 `bin/verify`

1. Target = sole occupant of doing/ (refuse if empty or ambiguous).
2. Read the verify block from the git-committed blob: `git show HEAD:tasks/doing/<id>.md`.
   Working-tree edits to the task file are inert (D20). Executors never commit,
   so HEAD's copy is the claim-time copy.
3. Attempt number (D28) = `git rev-list --count <claimCommit>..HEAD --grep
   '^muster(<plan>): attempt <n> <id>$'` + 1 - counting marker commits since the
   claim, not log content. If the count is already 3, go to step 7.
4. Append the `=== attempt <n>` header to the log and commit it alone, message
   `muster(<plan>): attempt <n> <id>` - the marker commit, burned BEFORE running
   any verify command so a killed verify still counts. Exit-code checked: a
   failed marker commit refuses rather than let an attempt run unaccounted. This
   is the ONLY per-attempt commit (D28); the transcript itself rides along in
   the next marker commit or the terminal done/fail commit.
5. Run each `cmd` in order (tokenized, direct invocation, timeout enforced).
   Append the transcript block. Stop at first failing entry.
6. All expectations met: print `VERIFY PASS (attempt <n>)`, exit 0.
   Otherwise: attempt < 3 = print `VERIFY FAIL (attempt <n> of 3): <first failed
   cmd and why>. Fix and rerun.`, exit 2.
7. Third failure: move task + verify.log + notes to failed/, commit
   (`muster(<plan>): fail <id>`), print `VERIFY FAIL terminal. Task moved to
   failed/ for human review. Session over.`, exit 3.

### 4.3 `bin/done [pass|fail]`

The verdict argument is required for review/integration tasks, forbidden for
impl/fix.

Common preconditions (any failure = `exit 1`, nothing moves):

1. Sole occupant of doing/ exists. `claim_commit` for all checks below is
   derived, not stored: `git log -n1 --format=%H -- "tasks/doing/<id>.md"` -
   the last commit touching the doing/ path is the claim commit, because
   executors never commit (RUNNER hard rule) and the completion commit has not
   happened yet.
2. Confirmation verify run (logged `=== done-check`) is attempted. This kills
   stale-pass: work changed after the last green attempt. Gating is conditional
   (D29): a `fail` verdict on a review or integration task proceeds even when
   this check is red - the red result is the finding a review/integration
   `fail` exists to report, not a discarded refusal. Every other case (all
   `pass` verdicts, and impl/fix tasks, which carry no verdict) still refuses on
   a red done-check: `MUSTER refuse: done-check verify failed: <first failed
   cmd>. Run the verify script, fix, and retry.`
3. Protected check (D20): `git diff --name-only <claim_commit>..worktree`
   intersected with `protected` must be empty. Violation names the files.
   Tracked diff only - untracked new files are deliberately excluded, so a task
   may create the protected test it grades (D30); once committed the file is
   tracked, and every downstream consumer's run of this same check freezes it.
   Do not fold the scope check's untracked arm into this check.
4. Scope check (D21, D27): every changed path must be in `commit_paths` or the
   executor-writable set under tasks/ (`doing/*.notes.md`, `doing/*.verify.log`,
   `staging/*.md`). A change to any other tasks/ path - bin/ scripts, RUNNER.md,
   task cards, done//failed/ history - refuses like any stray: the grading
   machinery is never the executor's to edit. Extras = refuse, message lists
   them (executor reverts strays or the human intervenes; the executor cannot
   widen commit_paths - the file is read-only to it).
5. Review/integration: notes file must exist.

`done` / `done pass` path:

6. Assemble result.md (section 3.1), fold + delete notes.
7. Move task + result.md + verify.log to done/.
8. Run promote in no-commit mode; stage its renames.
9. ONE completion commit (D21): commit_paths + sidecars + task rename +
   promotion renames. Message `muster(<plan>): done <id>`.
10. Print the counts-only board summary, then the terminal line (which stays
    literally last):
    `Board: run <n> | review <n> | backlog <n> (<n> DEAD) | failed <n> | done <n>`
    `Done: <id>. Promoted: <ids or none>. Do not claim another task. Session over.`
    Split rule as in 8.3: `invalid <n> |` appears after `review <n>` only when
    unparseable inbox files exist; `(<n> DEAD)` only when nonzero. No task ids -
    counts only. Success path only; the fail branches keep their own output.

`done fail` path for **review** tasks (tier-0 failures are `bin/verify`'s job):

6. Fix task must exist in staging/ - exactly one file, `fixes:` matching
   `reviews:` of the current task, staged gen-less (2.1). Run lint-lite (2.6)
   on it. A lint-lite refusal leaves the staged file in place - the reviewer
   session is live and fixes it, then reruns `done fail`.
7. Generation cap: g = count of existing `fixes: <impl-id>` files across
   tasks/ excluding staging/, plus one (2.2 - the script is the only counter).
   g = 3 = two fix generations already landed = **refuse to spawn** (D11):
   assemble result.md with `status: failed`, `verdict: fail`, move review task
   + sidecars to failed/, delete the staged fix, commit
   (`muster(<plan>): fail <id>`), print `Review cap hit (2 fix generations).
   <impl-id> chain needs a human. Session over.`, exit 3.
8. Under cap: stamp the staged fix - rename to the `fix<g>` filename, set `id`,
   `generation`, and the title line to match (2.1) - and move it to inbox/.
   Append the stamped fix id to the review task's own `depends_on`. Rename the
   round's sidecars to history:
   `<id>.verify.log` -> `<id>.gen<g>.verify.log`, and assemble this round's
   result as `<id>.gen<g>.result.md` (`status: cycled`, `verdict: fail`,
   findings folded), where `g` = the spawned fix's generation. No live
   verify.log survives the move, so the next round's attempt counter starts at
   1. Move the review task + history sidecars doing/ -> backlog/ (it
   re-promotes and re-runs when the fix lands - "fix carries review again",
   D11, with no new review task authored).
9. ONE commit: fix task + review task rename/edit + sidecars. Message
   `muster(<plan>): reject <impl-id> gen<g>`.
10. Print: `Review failed. Fix <fix-id> queued (generation <g> of 2). Session
    over.`

`done fail` path for the **integration** task `[spec decision]`:

6. No fix task is expected or accepted (staging/ must be empty). An integration
   failure is cross-task drift - plan-level, not one-impl-level: there is no
   `reviews`/`fixes` target for a fix task to point at, seq 99 is reserved, and
   a single cross-cutting fix task would itself violate the small-task
   principle. The response belongs to the orchestrator, not an executor.
7. Assemble result.md (`status: failed`, `verdict: fail`, findings folded),
   move task + sidecars to failed/, commit (`muster(<plan>): fail <id>`), print
   `Integration review failed. Bring tasks/failed/<id>.result.md to the
   orchestrator to shard a fix-up plan. Session over.`, exit 3.

`[spec decision]` - review cycling: on fail the review task returns to backlog/
blocked on the fix, instead of moving to failed/ or done/. Why: downstream tasks
depend on the review task's id (D19); done/ would release them onto rejected
code, failed/ would dead-block them permanently even after a fix passes.
Cycling preserves the DAG with zero dependent rewiring. The frontmatter edit
(appending the fix id) is performed by the script, not the model, so D17 holds.

### 4.4 `bin/promote [-NoCommit]`

1. Scan backlog/*.md frontmatter. A dependency is satisfied when a matching task
   id exists in done/ or anywhere under archive/ (D15).
2. Rename every fully satisfied task backlog/ -> inbox/. Order: filename
   ascending. Idempotent - nothing eligible = exit 0 silently.
3. Default: commit renames (`muster: promote <n>`). `-NoCommit`: stage renames
   only, for `bin/done` to fold into the completion commit (D21).

## 5. Git protocol (pinned)

- All transitions on main (D21). Claim = one small commit. Completion = ONE
  commit: code + sidecars + task rename + promotions.
- Executors never run git themselves - RUNNER forbids it; scripts do all
  staging and committing with explicit paths.
- Chronology per task: claim commit -> (work, uncommitted) -> completion commit.
  A crash between them leaves the claim commit + dirty tree; recovery per D12 is
  human, aided by the claim-probe (4.1 step 9).

## 8. Dispatch UX

### 8.1 Dispatch lines (the human types exactly one line)

Fresh Claude Code session, cwd = target repo:

- Execution session - model picker: **Sonnet 5**, then type `/muster:run`
- Review session - model picker: **Fable 5**, then type `/muster:review`
- Orchestrator loop - model picker: **Fable 5**, then type `/muster:auto`. Give
  it a plan id; it dispatches one Agent-tool subagent per task until the board
  settles, then closes the plan itself. See
  [subagent-orchestration design](2026-08-10-muster-subagent-orchestration-design.md)
  for the full loop and halt conditions.

Nothing is pasted back after the session - results live on disk; the
orchestrator reads sidecars whenever it next runs.

### 8.2 Wrapper skill texts (exact)

`/muster:run`:

```
Run `powershell -ExecutionPolicy Bypass -File tasks/bin/claim.ps1 -Harness claude -Tier any`
(POSIX: sh tasks/bin/claim.sh --harness claude --tier any), then follow
tasks/RUNNER.md to the letter.
```

`/muster:review`:

```
Run `powershell -ExecutionPolicy Bypass -File tasks/bin/claim.ps1 -Harness claude -Tier strong`
(POSIX: sh tasks/bin/claim.sh --harness claude --tier strong), then follow
tasks/RUNNER.md to the letter.
```

Codex wrapper (`.agents/skills/`, dormant until D16 gate passes): same text with
`-Harness codex`.

`/muster:auto` is not a thin wrapper like the three above - it is an
orchestrator loop with its own hard rules (sequential dispatch only, review
always a fresh subagent call). Full text: `skills/auto/SKILL.md`.

Every muster skill (wrappers and orchestrator skills alike) carries an
anti-trigger description: invoked ONLY by the explicit `/muster:<name>` slash
command, never auto-triggered by conversational mention of tasks, plans, or
dispatch. A wrapper auto-firing inside an orchestrator session would claim work
under the wrong identity; shard auto-firing would write task files before plan
approval.

### 8.3 Status print (claim step 2, exact format)

```
MUSTER status @ <repo-name> (<branch>)
  inbox    <n> ready      (run <n>, review <n>) [<ids, filename order>]
  doing    <n>            [<id> claimed <age>]        <- STALE if age > 24h: see RUNNER.md RECOVERY
  backlog  <n> blocked    (<n> DEAD: <id> behind failed <dep-id>)
  failed   <n>            [<ids>]
  done     <n>
```

- STALE marker and DEAD lines appear only when present. DEAD = a backlog task
  with any dependency in failed/ (D12).
- Empty board prints `MUSTER: board empty - nothing sharded or all archived.`
- Dispatch split: `run` counts `tier: any` inbox tasks, `review` counts
  `tier: strong` (claim's two-way tier pinning makes these exactly what
  `/muster:run` and `/muster:review` can claim). Always printed, zeros
  included. Inbox files with unparseable frontmatter or an illegal tier count
  toward `<n>` and toward neither bucket; when any exist, `, invalid <n>` is
  appended inside the parentheses. Parse-level check only - no schema
  validation at print time, and "unparseable" is as strict as the engine's own
  frontmatter parser (ps1 rejects more defect classes than sh), so the invalid
  count on a hand-damaged board may differ between engines. Boards of
  schema-valid tasks print identically on both.
- Three callers share this block: `claim` step 2, `bin/status` (on-demand,
  not a RUNNER verb), and `done`'s counts-only `Board:` summary line (4.3)
  reuses the same split and DEAD scan.

### 8.4 Refusal messages (exact wording)

| Condition | Message |
|---|---|
| dirty tree out of scope | `MUSTER refuse: working tree dirty outside <id>'s commit_paths: <paths>. Likely leftovers from a failed or crashed task - see RECOVERY (RUNNER.md), 'leftover dirt'.` |
| doing/ occupied | `MUSTER refuse: doing/ occupied by <id> (claimed <age> ago). One executor per checkout. RECOVERY in RUNNER.md.` |
| staging/ not empty | `MUSTER refuse: stale fix task in tasks/staging/: <file>. Human clears it - RECOVERY in RUNNER.md.` |
| nothing eligible | `MUSTER refuse: nothing to claim for <harness>/<tier>.` |
| malformed frontmatter | `MUSTER refuse: <id> frontmatter invalid: <first error>. Task left in inbox/ for a human.` |
| protected touched | `MUSTER refuse: protected file(s) modified: <paths>. Revert them; the verify definition is not yours to change.` |
| out-of-scope changes | `MUSTER refuse: changed outside commit_paths: <paths>. Revert strays or stop for a human.` |
| notes missing (review/integration) | `MUSTER refuse: verdict needs tasks/doing/<id>.notes.md with findings.` |
| staged fix missing/invalid | `MUSTER refuse: done fail needs exactly one valid fix task in tasks/staging/ (<first lint error>). File left in place - fix it and rerun.` |
