# Decision ledger

Settled direction with rationale. Open to challenge, but reopening one means re-arguing its "why".

## D1. Requirement = delegate-and-forget agentic flow

Fresh-context executors, harness-agnostic, manual dispatch v1, automation end-state.
Fresh context and multi-harness both matter, but durability + delegation is the core driver.
Why: context rot makes one-session whole-plan execution degrade; copy-paste dispatch is the pain being killed.

## D2. Two-plane architecture

Data plane = task files in the target repo. Control plane = ASP.NET + SQL Server app, later, read-side only.
Why: files are the only interface every harness speaks with zero config.
The app must never sit in the agent critical path - app down must not stop agents.

## D3. Agents touch files only, never DB/HTTP

Why: Codex workspace-write sandbox blocks network by default (localhost SQL and HTTP included).
Cheap-model CLIs may have no MCP or skill support at all; every one of them can read a file.
Files are git-versioned, atomic-rename claimable, and human-inspectable.

Re-challenged and re-rejected this session: "MUSTER as ASP.NET app with agents querying API/MCP".
Fails on critical path (app must be up for any agent to work), bootstrap paradox (the pipeline would depend on an app the pipeline is supposed to build), and sandbox friction.
Everything wanted from the app (registry, rich statuses, dashboards, query UX) survives as a read-side mirror fed FROM files.

## D4. Ride superpowers, don't replace it

Planning stays 100% existing superpowers (brainstorming, writing-plans, plan-reviewer, yagni-guardian gates).
MUSTER adds one new final step: `muster:shard` converts an approved plan into task files.
Why: planning quality tooling already exists and works; replacing it means rebuilding it worse.
The plan doc stays the shared context anchor - executors read one small task plus targeted plan sections.

## D5. MUSTER plugin = thin layer, not a fork

Plugin contains only muster-specific skills (init / shard / run). Zero superpowers files copied or modified.
Why: forks drift; superpowers updates would rot a copy.
Opt-in comes free: small tasks use the normal path; MUSTER engages only when its skills are invoked.

## D6. Canonical executor contract = tasks/RUNNER.md

Logic lives in one plain file in the target repo. Skill wrappers per harness are 3-line pointers.
Codex discovers repo skills in `.agents/skills/` ($muster-run); Claude gets a plugin skill (/muster:run).
Why: executor logic in plugin-only would silently break non-Claude harnesses.
No symlinks - unreliable on Windows + git. Thin pointer files instead.

## D7. Executor promotes unblocked tasks as its final act

After moving its own task to done/, the executor moves any backlog task whose depends_on are all done into inbox/.
Why: completion is the only event that unblocks work; v1 has no app and the orchestrator session may be dead.
Bends "implementers stay dumb" slightly, but the rule's purpose was no JUDGMENT in executors - this is pure frontmatter mechanics.
Races are safe: rename is atomic, the second mover just fails harmlessly.

## D8. Executors open inside the target repo

cwd = project. The executor reads ./tasks/ and nothing else. No registry lookup executor-side.
Why: sandbox-safe (Codex workspace-write), zero path resolution for weak models, git ops natural.
Consequence: registry.json is demoted to orchestrator/app concern, out of the v1 critical path.

## D9. Weak-executor principle

The orchestrator (strong model) does ALL thinking at shard time: explicit steps, exact paths, acceptance criteria, verify commands.
Executors get zero judgment calls.
Why: executors are cheap models by design; also small sharp tasks survive weak long-context handling.
Pay for judgment once (shard time, review time), not per execution step.

## D10. Two-tier verification

Tier 0: deterministic verify block, mandatory, executor loops run-fix-rerun capped at 3, then failed/ with logs.
Tier 1: agent review as a NEW TASK (not a status), flagged by the orchestrator at shard time, generated by the executor from a template, pinned to a strong model, checking only what code cannot test.
Hard rule: no task without a machine-testable end condition; un-checkable work gets weak verify + forced review.
Why: reliability order is code > engineers > agents. Deterministic checks cost near-zero judgment tokens.
Review-as-task keeps the agent contract tiny; fine statuses live in the control plane later.
Cheap-model executors must not review their own work - judgment is pinned to strong models.

## D11. Redo flow = natural loop, no cap in v1

Review fail = reviewer creates a fix task pointing at findings; fix carries review: required again.
Why: the ping-pong is visible in folders; the human can step in. Caps/escalation are a v2 app concern.

## D12. Stale doing/ = automated detection, human recovery

muster:run prints stale claims (claimed_at old, still in doing/). Recovery is manual: human checks git state, moves the file back to inbox/ or to failed/.
No auto-reclaim by timeout.
Why: auto-reclaim's failure mode is two executors interleaving work on a dirty tree - corrupting.
Manual recovery's failure mode is delay - boring. Choose the design whose failure is boring.

## D13. Multiple task lists per project

Real requirement: one project can hold several sharded plans, possibly concurrent.
Direction: flat status folders stay; a `plan` field in task frontmatter groups tasks. No folder-per-plan (folder explosion).
Schema detail not finalized.

## D14. Sequencing

v1 file convention + plugin, zero build. v2 ASP.NET viewer built through the pipeline (dogfood). v3 app-managed workflow richness + possible programmatic dispatch.
Why: v1 must exist before the app can be built BY it.

## Rejected (do not reopen without new facts)

- **A2A protocol** - enterprise HTTP mesh; harness CLIs don't speak it.
- **DB-as-store / webapp-as-store** - split-brain with file-shaped work, sandbox friction, critical-path and bootstrap failures (see D3).
- **Folder-per-status-explosion** (review folders, per-plan folders) - coarse status = folder, fine status = control plane later.
- **Fork superpowers into the plugin** - drift, double maintenance (see D5).
- **Auto-reclaim stale tasks by timeout** - corrupting failure mode (see D12).
- **Symlinked skills across harnesses** - Windows + git symlink reliability (see D6).

## KIV (revisit later, do not delete)

- Programmatic dispatch: claude -p / codex exec, verified possible and resumable by session id. Needs permission presets for headless children.
- Vibe Kanban (too heavy for now), beads (git-backed issue DB) as prior art.
- App-backed MCP for human/orchestrator queries (v2+).
- External code-node verification with session-ID route-back (v3, requires programmatic dispatch).
